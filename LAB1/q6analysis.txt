**Method used:** Sort-then-scan. The array is sorted with `qsort` (which uses an introsort/quicksort variant, average and typical-case O(n log n), worst case O(n²) though this is rare in practice), then a single linear pass checks each element against its neighbor for equality.

**Correctness:** After sorting, any duplicate values are guaranteed to sit adjacent to each other, so a single O(n) scan is sufficient to detect them — no need to compare every pair.

**Time complexity:** O(n log n) overall, dominated by the sort step; the scan itself is only O(n) and doesn't change the asymptotic bound.

**Space complexity:** O(1) auxiliary (in-place sort), aside from O(log n) recursion stack space used internally by qsort.

**Conclusion for sufficiently large n:**
Benchmarking confirms the n log n scaling in practice:

| n | time |
|---|---|
| 1,000 | 0.00007 s |
| 10,000 | 0.00083 s |
| 100,000 | 0.01006 s |
| 1,000,000 | 0.12238 s |
| 5,000,000 | 0.69623 s |

Going from 1M to 5M elements (5× the input) only increases runtime by ~5.7×, not 25× — which is exactly what you'd expect from O(n log n) growth rather than O(n²). This means the method remains practical even for very large n, unlike a naive nested-loop duplicate check (compare every pair, O(n²)) which would become prohibitively slow at these sizes (e.g., 5M² = 2.5×10¹³ comparisons).

**Trade-off worth mentioning:** A hash-set-based approach could do this in O(n) average time by inserting elements into a set and checking for collisions, at the cost of O(n) extra space. So the sort-based method is a good time-space balance: it's slower than a hash set asymptotically but needs no extra memory, which matters for very large n or memory-constrained environments.
